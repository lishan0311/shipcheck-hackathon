# ShipCheck

An English-language shipping document verification workspace.

The interface uses a small project-owned PNG icon set generated by
`scripts/generate_ui_icons.py`.

## Technology stack

| Layer | Implementation |
|---|---|
| Frontend | TypeScript, React, Vite, Tailwind CSS, React Router |
| API client | Browser Fetch API |
| Backend | Python, FastAPI, Pydantic |
| Email classifier | scikit-learn, TF-IDF, Logistic Regression, joblib, explicit workflow-intent rules |
| Documents | pdfplumber, pypdfium2, python-docx, openpyxl |
| OCR | Tesseract and pytesseract |
| Field extraction / comparison | Python regex, alias mapping, Decimal |
| Persistence | Supabase PostgreSQL and private Supabase Storage |
| Container / hosting | Docker, Render |
| Tests / collaboration | pytest, organizer scoring export, GitHub CI |

The earlier vanilla JavaScript frontend, WSGI server and active SQLite persistence have been replaced. The old SQLite file remains untouched for explicit migration.

## Local setup on Windows

Use Python 3.12 or 3.13 and Node.js 22. From the project root:

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r requirements.txt
.venv/Scripts/python.exe -m model.train
Copy-Item .env.example .env
```

Do not overwrite an existing `.env` containing your credentials. Fill in Supabase settings as described below, or explicitly leave `ALLOW_DEMO_MODE=true` to try the app without cloud credentials.

In `frontend/`:

```powershell
npm.cmd ci
npm.cmd run build
```

Back in the project root:

```powershell
# Open immediately with temporary in-memory data:
python run.py --demo

# After the Supabase migration is installed:
python run.py
```

Open **http://127.0.0.1:8000**. The launcher uses the project virtual environment if the system Python lacks Uvicorn. Keep the terminal open.

For frontend development, keep FastAPI running on 8000, run `npm.cmd run dev` in `frontend/`, and open **http://127.0.0.1:5173**. Vite proxies `/api` to FastAPI.

The current checkout already has dependencies, a model and a frontend production build.

## Supabase settings

Run `supabase/migrations/001_shipcheck.sql` in your Supabase SQL editor. Existing projects should then run `002_inbox_summary.sql` and `003_review_outcome_summary.sql` in order. Fill the root `.env`:

```dotenv
SUPABASE_URL=https://YOUR_PROJECT.supabase.co
SUPABASE_SERVICE_ROLE_KEY=YOUR_BACKEND_ONLY_SERVICE_ROLE_KEY
SUPABASE_BUCKET=shipping-documents
ALLOW_DEMO_MODE=false
```

Restart the app, process an email and verify the database rows and private storage objects. Do not put this key in frontend code or any `VITE_*` variable.

Without credentials, the explicit local demo uses memory and clearly says so in the UI. Its new reports disappear on restart. There is no silent SQLite fallback. The previous `runtime/shipcheck.sqlite3` is preserved; `scripts/import_legacy.py` supports a one-time import after Supabase is configured.

## Pages and behavior

- `/inbox`: searchable email workspace.
- `/emails/:emailId`: classification, seven-field comparison, original sources and run history.
- `/review`: action queue for uncertain/failed cases and reviewed cases ready to contact.
- `/review/:emailId`: confirm the email category, correct extracted values and record a reason.

Use **Process inbox** in the top bar to process all supplied emails that do not yet have a saved report. The button is disabled once the inbox is complete. While a batch runs, its progress bar is visible below the KPI cards and disappears when the batch finishes. An operator can re-run an individual email after a model or extraction update; each new report is appended, so the previous audit history remains available. Inbox refreshes use compact summaries while complete evidence remains available on each detail page.

| Required category | System action |
|---|---|
| BL comparison request | Read the SI and draft BL, compare seven fields and report mismatches |
| New shipping instruction request | Classify and route; no document comparison |
| Invoice query | Classify and route to billing or finance; no document comparison |
| General operational email | Classify and route; no document comparison |
| Spam | Classify with no operational action |

Clear recurring workflow phrases resolve the supplied SI and draft-BL templates; free-form text is classified by TF-IDF + Logistic Regression. Only resolved BL comparison requests enter document checking. Category ambiguity, document-reading problems, missing values and discrepancies appear in the action queue. A reviewer records a business decision: confirm a discrepancy, request missing information, correct a system extraction, accept a party-name presentation difference as equivalent, or confirm the workflow. Source documents remain unchanged. Confirmed discrepancies become follow-up cases. **Send all follow-ups** previews and sends every reviewed, ready-to-contact case through Gmail, then moves successful cases to **Waiting for response**.

When Gmail is configured, the backend polls the authorized Inbox, imports new messages and supported TXT/PDF/DOCX/XLSX attachments, places the newest email at the top and processes it immediately. It also reads the Sent mailbox for messages containing the generated `[SC-email_id]` reference. A detected sent follow-up moves the case to **Waiting for response**; an Inbox reply with the same reference is attached to the original case and moves it to **Response received**. The **Sync Gmail** action performs the same synchronization on demand. Stable IDs prevent the same message from being imported twice.

Reviewer names are self-reported. The optional workspace access token is a shared demo gate, not individual authentication. It is stored only for the browser session.

The application initially reads the participant inbox from the bundled dataset. Processing synchronizes the email and its original attachments to Supabase. New Gmail messages use the same processing and persistence path.

## Real Gmail / Google Workspace inbox

1. Open Google Cloud Console, create or select a project, and enable **Gmail API**.
2. Configure the OAuth consent screen. While the app is in testing, add the Gmail account under **Test users**.
3. Create an OAuth client of type **Web application** and add this exact authorized redirect URI: `http://127.0.0.1:8765/callback`.
4. Put the client ID and client secret in the root `.env`, then run the local authorization helper:

```powershell
.venv/Scripts/python.exe scripts/gmail_oauth.py --write-env
```

Sign in to the inbox account and approve Gmail read and send access. The helper saves the returned refresh token only to the local `.env`. Complete these variables:

```dotenv
MAIL_PROVIDER=gmail
GMAIL_CLIENT_ID=YOUR_GOOGLE_OAUTH_CLIENT_ID
GMAIL_CLIENT_SECRET=YOUR_GOOGLE_OAUTH_CLIENT_SECRET
GMAIL_REFRESH_TOKEN=CREATED_BY_THE_LOCAL_HELPER
GMAIL_USER_ID=shipping.operations@gmail.com
MAIL_POLL_SECONDS=15
MAIL_SYNC_LIMIT=25
```

Copy the same five Gmail values to the Render service environment and restart it. The header changes to **Gmail · mailbox-address** after the first successful synchronization. Send an email to `GMAIL_USER_ID`; it should appear at the top within the polling interval and will be processed automatically. The app requests `gmail.readonly` and `gmail.send`; keep the client secret and refresh token out of GitHub and frontend variables. If a Workspace administrator restricts third-party OAuth apps, they must allow this OAuth client.

For an external OAuth app left in **Testing**, Google expires the refresh token after seven days. Re-run the helper before judging, or move the consent screen to **In production** after completing Google's requirements. Internal Google Workspace apps are governed by the organization's admin policy.

## Documents and evidence

TXT is read as UTF-8. Word paragraphs/tables and Excel rows preserve their source locations. Text PDFs use pdfplumber with page bounding boxes. Pages with no extractable text are rendered by pypdfium2 and sent to Tesseract through pytesseract.

On Windows, set `TESSERACT_CMD` to your installed executable for actual OCR. The Dockerfile installs Tesseract and English language data automatically.

OCR and spreadsheet formulas remain conservatively flagged for review. This version cannot waive OCR warnings or replace missing/ambiguous documents through the review form. Human field corrections can resolve missing/extracted-value issues, but do not erase structural document problems.

Known field labels, bilingual carrier forms and simple tabular layouts are supported. Complex layouts and ambiguous formats may still need review. Weights use exact Decimal normalization with comma thousands and dot decimals; the workflow schema supplies kilograms when a form omits the unit, while explicit metric-tonne values are converted. No arbitrary tolerance is used.

## Model and tests

The baseline uses 60 assistant-authored synthetic training emails and 15 separately authored validation emails. A small, documented rules layer handles unambiguous recurring shipping templates before the model result is used. Synthetic validation is not an official dataset score or proof of production accuracy. Model probabilities are uncalibrated.

Keep three measurements separate: the synthetic model validation measures only the small authored split; the organizer scorer measures the complete rules-plus-model pipeline on the supplied 520 records; `scripts/evaluate_reviewed_categories.py` measures agreement on real emails that people have reviewed. The last metric is biased if reviewers inspect only difficult cases, so review a random, category-balanced sample as well as the automatic review queue. Use confirmed mistakes as new labelled data, keep senders/templates grouped into one split to prevent leakage, retrain, and compare against a frozen validation set before replacing the saved model.

```powershell
.venv/Scripts/python.exe -m pytest -q
.venv/Scripts/python.exe -m model.train
.venv/Scripts/python.exe -m backend --email-id email_001 --process --json
.venv/Scripts/python.exe scripts/evaluate_reviewed_categories.py
.venv/Scripts/python.exe scripts/export_submission.py --output runtime/submission-current.json
.venv/Scripts/python.exe scripts/evaluate_supplied_dataset.py
```

For a second deterministic dataset with different shipments and injected
defects, install `requirements-evaluation.txt`, run the organizer generator
with a new seed, then evaluate from source with `--run-pipeline`. This is a
stronger regression check than repeatedly tuning against the supplied answer
key, although synthetic generator performance still does not prove real Gmail
accuracy.

```powershell
.venv/Scripts/python.exe -m pip install -r requirements-evaluation.txt
.venv/Scripts/python.exe sdoc-hackathon-docker/data_v2/generate.py --seed 73 --n 500 --out runtime/holdout-seed-73
.venv/Scripts/python.exe scripts/evaluate_supplied_dataset.py --dataset runtime/holdout-seed-73 --run-pipeline --output runtime/evaluation-holdout-seed-73.json
```

`frontend/package-lock.json` locks frontend dependencies. Python top-level dependency versions are pinned in `requirements.txt`.

The tests cover classification, routing, field comparison, readers, API contracts, human corrections, stale-review protection, Supabase HTTP adapter behavior and scoring export. Native OCR, live Supabase and Docker are separate integration checks and are not implied by passing mocked tests.
